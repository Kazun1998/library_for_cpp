# ライブラリのドキュメントを書く

`oj-verify` は `Document/<Topic>/<Name>.md` を `.hpp` と対応づけて GitHub Pages のサイトを作る。サイトは Jekyll (kramdown + MathJax) で組まれるので、**普通のマークダウンでは問題ない記述でも、数式やコード例が壊れることがある**。以下は Todd–Coxeter 法と Digit (整数の桁) のドキュメントを書いたときに、実際に踏んだ問題と決まった書式をまとめたもの。

## 進め方

1. **周りを読む**: 同じトピックのドキュメントと、書式の手本 (`Document/Others/Topological_Sort.md`, `Document/Algebra/Nimber.md`) を先に読む。列/文字列を扱うなら `.verify-helper/docs/static/String.md` (記法の取り決め)。独自の書式を作らず、周りに合わせる。
2. **実装を確定してからドキュメントを書く**: API 名・引数・計算量がコードと食い違わないようにする。コードを直したらドキュメントも直す (旧 API の記述が残りやすい)。
3. **主張は実行して確かめる**: 具体例の値 (位数、一致・不一致など)、計算量の見積もりに使う実測値は、実際にコンパイルして実行して確かめてから書く。確かめていない定理の出典や「必ず終了する」のような主張は書かない。
4. **描画を確かめる**: `ruby -e 'require "kramdown"; ...'` で `input: "GFM"` として HTML にし、`<em>` が数式の中に紛れていないかを見る (下の「表示崩れ」参照)。Jekyll 自体はローカルに無いことが多い。確認できない部分は、確認できていないと報告する。
5. **ユーザーが書いた定義は尊重する**: 定義や命題をユーザーが自分で書き換えたときは、その番号・記法に合わせて残りの本文を直す。番号の衝突 (定義 3 のあとに別の命題 2 が残る等) が起きやすいので、書き換えのたびに番号と参照 (「命題 12 より」など) を全文検索して揃える。
6. **編集の直前に読み直す**: ユーザーは作業の合間にエディタでファイルを直接書き換える (Digit では、修正を当てている間に Theory 節の構成が変わり、命題が追加されていた)。まとめて置き換える前に必ず読み直し、置き換え元が見つからないときは上書きせず、ユーザーの新しい構成に合わせて修正を当て直す。
7. **引数の想定範囲は作者の意図を確認する**: 実装の挙動から仕様を推測して書かない。Digit では `abs(N)` があるのを見て「符号は無視される」「$N \neq -2^{63}$」と書いたが、作者の想定は $N \geq 0$ だった。境界の挙動 (負数・0・オーバーフロー) を見つけたら、制約として書く前に「どこまでを想定しているか」を聞く。
8. **レビューを頼まれたら、まずレビューだけ返す**: 指摘には番号を振り (ユーザーは「(1), (2), (3) を修正」のように選ぶ)、修正は指示を待つ。直す範囲も指示どおりにする (「ドキュメントを修正」ならヘッダのコメントは触らずに報告する)。

## 文書の構成

```
---
title: <名前>
documentation_of: //<Topic>/<Name>.hpp
---

## Outline    何を求めるか。戦略。計算量・制約のひとこと。
## Define     記法・用語・入出力の取り決め。
## Theory     一般論 (定義・命題・証明)。
## Contents   ### <関数名> ごとにシグネチャ・説明・**制約**・**計算量**。
## History    |日付|内容| の表 (新しい順)。
```

* Theory は一般論として書き、**有限性などの仮定を勝手に置かない**。
* Theory は `###` で細かく切らない。「理論付け」と「アルゴリズム」くらいの粒度。具体例が要るなら `### 具体例` を作り、その下は `####`。
* 定義・命題・証明は次の形式で囲む (見出しは `---` のセットアップ見出し):

  ```markdown
  <div class="proposition" markdown="1">

  命題 3
  ---

  ...

  </div>

  <div class="proof" markdown="1">

  証明
  ---

  ...

  </div>
  ```

  種類は `definition` / `proposition` / `theorem` / `corollary` (系) / `lemma` (補題) / `proof` / `remark` (ほかに `problem` / `box`)。枠のスタイルは `.verify-helper/docs/static/assets/css/style.scss` で定義されたクラスにしか付かないので、`theory` のような未定義のクラスを使うと枠なしで表示される。番号は定義・命題・定理・系・補題・注意で通し番号。
* Contents の各関数は、コードブロックのシグネチャ → 箇条書きの説明 → `* **制約**` / `* **計算量**` (その下に入れ子で内容)。
* 計算量は、記号 (`N`, `K`, `L` など) を定義してから導出を Theory に書き、Contents には結論と参照だけを書く。決定不能な問題が絡むときは、**なぜ上界を示せないか**まで書く。
* Contents の用語は Theory の定義と揃える (Theory で「数字和」と定義したら、Contents も「桁和」ではなく「数字和」)。
* Contents の **制約** には、引数の範囲 (例: $N \geq 0$, $b \geq 2$) と、満たさないときの挙動 (例外が送出されるか) を書く。

## 定義・命題・証明の書き方

* **有限列は長さの情報も含む**。存在・一意性を述べるときに「正の整数 $d$ と列 $a$ の組 $(d, a)$ がただ一つ存在する」とは書かない。「以下を満たす整数の有限列 $a$ がただ一つ存在する. ただし, $d$ を $a$ の長さとして, $a = (a_{d-1}, \dots, a_0)$ と添字を付ける.」のように書く。
* 記号は使う前に導入する (条件の中に出てくる $d$ が未定義、など)。
* 定義で定理の条件をそのまま繰り返さない。「定理 1 の列を $a$ とする」のように参照する。
* 定理の対象外の値 ($n = 0$ など) は、定義で補う (「$0$ の $b$ 進表記は空列とする」)。補った定義が Contents の挙動 (`Integer_Length(0) = 0` など) と食い違わないか確認し、食い違う関数には注意書きを付ける。
* 命題には証明を付ける。ユーザーが命題を書いたら、式の誤り (法が $b-1$ のところ $d-1$、値が $b-1$ のところ $b$ など) を総当たりで確かめてから指摘する。

## 数式・記法の規約

* 同値な命題同士は **(a), (b)** で番号付ける ((1), (2) は使わない)。
* 部分集合は等号を含んでいても **`\subset`** (`\subseteq` は使わない)。
* アルファベットは `X`、文字は `x \in X`、文字列全体は `X^\ast`。空列は `\emptyset`、結合は `\oplus`、長さは `\lvert \alpha \rvert`。モノイドの単位元は `e`。
* 集合の波括弧は `\lbrace` `\rbrace` (`\{` はマークダウンに食われる)。絶対値・長さは `\lvert` `\rvert` (`|` は表の区切りと誤解される)。
* 見出しには数式を入れない (`### $b$ 進表示` ではなく `### b 進表記`)。
* 法が式のときは括弧を付けて **`\pmod{(b-1)}`** と書く (`\pmod{b-1}` は使わない)。整除は `|` ではなく **`\mid`**。
* 周りのドキュメントにある用語 (「列/文字列」ページ) へはリンクで参照する。
* 幾何の点は `\textrm{P}` (2 点を並べるときも `\textrm{A}\textrm{B}`)。`\mathrm` や裸の `P` を混ぜない。

## 証明の書き方

* **天下り的な証明は避ける**。答え (交点・最小値を取る点など) を先に「$\textrm{G} = \dots$ とおく」と与えて条件を満たすことを確かめる形ではなく、条件から連立方程式を立てて解くなどして**導出する**形にする。導出した値を使ってほかの条件を確かめる変形 (例: 中線 AL, BM の交点として求めた $\textrm{G} = \frac{\textrm{A}+\textrm{B}+\textrm{C}}{3}$ を $\frac{1}{3}\textrm{C} + \frac{2}{3}\textrm{N}$ と変形して CN 上にあることを示す) はよい。
* 対象が存在して一意であることを先に命題で示し、そのあとで定義に名前を付ける (命題「…を満たす点がただ一つ存在する」→ 定義「その点を…という」)。存在・一意性の主張を `definition` の枠に入れない。
* 実装で使う具体的な式 (射影の式 $\textrm{H} = \dots$ など) は、特徴付けの命題に含めず**系**として分け、直前に「次の系によって…を具体的に計算することが可能になる」と一言添える。

## 表示崩れを避ける (kramdown / Jekyll)

* **1 行に `*` が 2 個以上**あると強調と解釈されて崩れる。`X^*` は `X^\ast` と書く。
* **記号の直後の `_`** (`]_\equiv`, `}_M` など) が同じ段落に 2 個以上あると、強調の開始・終了と解釈されて数式が壊れる。英字の直後の `_` (`\sim_R`, `x_1`) は問題ない。`[\alpha]_\equiv` のような書き方は `\overline{\alpha}` などに置き換える。
* **`#` はインライン数式 `$...$` の中では `\\#`** と書く。kramdown が数式として扱うのは `$$ ... $$` だけなので、`$\#$` の `\#` はマークダウンのエスケープとして `#` になり、MathJax がマクロ引数の記号と解釈してエラーになる (Manacher で `$\# \notin X$` などが全滅した)。別行立ての `$$ ... $$` の中は kramdown がそのまま渡すので `\#` のままにする (`\\#` にすると逆に崩れる)。既存の文書 (`Document/Modulo/Order.md`, `.verify-helper/docs/static/Graph.md`) も `$\\# V$` の形。`\{` を `\lbrace` にするのと同じ理由。
* **`{{` や `{%`** が本文やコードブロックにあると、Jekyll の Liquid が変数・タグと解釈して `Liquid syntax error` になる (例: `Todd_Coxeter M(1, {{{0, 0, 0}, {}}});`)。該当するコードブロックは、フェンスの外側の行に `{% raw %}` と `{% endraw %}` を置いて囲む。数式では `\lbrace` を使うので `{{` は出ない。
* ドキュメント生成のエラーはローカルで再現できないことが多い。エラーメッセージの行番号 (Liquid は変換前の行) から原因の記号を探す。

## 検証 (verify) ファイルを書く

* 置き場所: アルゴリズム単体の検証は `verify/original/<Name>.test.cpp`、ジャッジの問題を使うものは `verify/<judge>/<category>/`。
* `verify/original` は `#define PROBLEM "https://judge.u-aizu.ac.jp/onlinejudge/description.jsp?id=ITP1_1_A"` を先頭に置き、`verify()` に `assert` を並べ、`main` で `verify(); cout << "Hello World" << endl;` とする (既存の `Double_Add_Convolution.test.cpp` などに倣う)。
* CI は `g++-13 -std=c++23 -O3 -Wall -g` で全件実行する。**ヘッダの API を変えたら、旧 API を使う検証ファイルが壊れていないか必ず確認する** (今回も、旧版の群用 API が残っていた)。
* 位数や既知の値との一致、作用表の整合性、小さい例での全探索との突き合わせなど、**実装と独立な根拠**でテストする。無限になる入力など、終了しないものはテストにしない。
* 期待値は定義から作る (例: Digit では、返り値が定理 1 の条件を満たすかを `__int128` で判定する関数を書いた)。ドキュメントの Theory に書いた命題も、ライブラリの関数を使ってテストに入れる。
* 境界の値 (0, 空列, `LLONG_MAX`, 底が値より大きい場合など) と、不正な引数で例外が送出されることもテストする。
* 単体の確認は `oj-verify run verify/original/<Name>.test.cpp` で行う。

## コミット・ブランチ

* `main` に直接コミットしない。ブランチ名は `feature/<name>` (ドキュメントのみなら `doc/<name>` もある)。
* コミットメッセージは `feature:` / `docs:` / `fix:` / `refactor:` / `test:` などの接頭辞 + 日本語の要約。本文に変更ファイルを列挙してよい。
* ヘッダの変更・ドキュメントの変更・テストの追加は、別々のコミットに分ける。
* 関係のないファイル (他のトピックの未追跡ファイル) はコミットに含めない。プッシュや PR 作成は、頼まれたときだけ行う。
