# ライブラリのドキュメントを書く

`oj-verify` は `Document/<Topic>/<Name>.md` を `.hpp` と対応づけて GitHub Pages のサイトを作る。サイトは Jekyll (kramdown + MathJax) で組まれるので、**普通のマークダウンでは問題ない記述でも、数式やコード例が壊れることがある**。以下は Todd–Coxeter 法のドキュメントを書いたときに、実際に踏んだ問題と決まった書式をまとめたもの。

## 進め方

1. **周りを読む**: 同じトピックのドキュメントと、書式の手本 (`Document/Others/Topological_Sort.md`, `Document/Algebra/Nimber.md`) を先に読む。列/文字列を扱うなら `.verify-helper/docs/static/String.md` (記法の取り決め)。独自の書式を作らず、周りに合わせる。
2. **実装を確定してからドキュメントを書く**: API 名・引数・計算量がコードと食い違わないようにする。コードを直したらドキュメントも直す (旧 API の記述が残りやすい)。
3. **主張は実行して確かめる**: 具体例の値 (位数、一致・不一致など)、計算量の見積もりに使う実測値は、実際にコンパイルして実行して確かめてから書く。確かめていない定理の出典や「必ず終了する」のような主張は書かない。
4. **描画を確かめる**: `ruby -e 'require "kramdown"; ...'` で `input: "GFM"` として HTML にし、`<em>` が数式の中に紛れていないかを見る (下の「表示崩れ」参照)。Jekyll 自体はローカルに無いことが多い。確認できない部分は、確認できていないと報告する。
5. **ユーザーが書いた定義は尊重する**: 定義や命題をユーザーが自分で書き換えたときは、その番号・記法に合わせて残りの本文を直す。番号の衝突 (定義 3 のあとに別の命題 2 が残る等) が起きやすいので、書き換えのたびに番号と参照 (「命題 12 より」など) を全文検索して揃える。

## 文書の構成

```
---
title: <名前>
documentation_of: //<Topic>/<Name>.hpp
---

## Outline    何を求めるか。戦略。計算量・制約のひとこと。
## Define     記法・用語・入出力の取り決め。
## Theory     一般論 (定義・命題・証明)。
## Contents   ### <関数名> ごとにシグネチャ・説明・**制約**・**計算量**。
## History    |日付|内容| の表 (新しい順)。
```

* Theory は一般論として書き、**有限性などの仮定を勝手に置かない**。
* Theory は `###` で細かく切らない。「理論付け」と「アルゴリズム」くらいの粒度。具体例が要るなら `### 具体例` を作り、その下は `####`。
* 定義・命題・証明は次の形式で囲む (見出しは `---` のセットアップ見出し):

  ```markdown
  <div class="proposition" markdown="1">

  命題 3
  ---

  ...

  </div>

  <div class="proof" markdown="1">

  証明
  ---

  ...

  </div>
  ```

  種類は `definition` / `proposition` / `proof` / `remark`。番号は定義・命題・注意で通し番号。
* Contents の各関数は、コードブロックのシグネチャ → 箇条書きの説明 → `* **制約**` / `* **計算量**` (その下に入れ子で内容)。
* 計算量は、記号 (`N`, `K`, `L` など) を定義してから導出を Theory に書き、Contents には結論と参照だけを書く。決定不能な問題が絡むときは、**なぜ上界を示せないか**まで書く。

## 数式・記法の規約

* 同値な命題同士は **(a), (b)** で番号付ける ((1), (2) は使わない)。
* 部分集合は等号を含んでいても **`\subset`** (`\subseteq` は使わない)。
* アルファベットは `X`、文字は `x \in X`、文字列全体は `X^\ast`。空列は `\emptyset`、結合は `\oplus`、長さは `\lvert \alpha \rvert`。モノイドの単位元は `e`。
* 集合の波括弧は `\lbrace` `\rbrace` (`\{` はマークダウンに食われる)。絶対値・長さは `\lvert` `\rvert` (`|` は表の区切りと誤解される)。
* 見出しには数式を入れない。
* 周りのドキュメントにある用語 (「列/文字列」ページ) へはリンクで参照する。

## 表示崩れを避ける (kramdown / Jekyll)

* **1 行に `*` が 2 個以上**あると強調と解釈されて崩れる。`X^*` は `X^\ast` と書く。
* **記号の直後の `_`** (`]_\equiv`, `}_M` など) が同じ段落に 2 個以上あると、強調の開始・終了と解釈されて数式が壊れる。英字の直後の `_` (`\sim_R`, `x_1`) は問題ない。`[\alpha]_\equiv` のような書き方は `\overline{\alpha}` などに置き換える。
* **`{{` や `{%`** が本文やコードブロックにあると、Jekyll の Liquid が変数・タグと解釈して `Liquid syntax error` になる (例: `Todd_Coxeter M(1, {{{0, 0, 0}, {}}});`)。該当するコードブロックは、フェンスの外側の行に `{% raw %}` と `{% endraw %}` を置いて囲む。数式では `\lbrace` を使うので `{{` は出ない。
* ドキュメント生成のエラーはローカルで再現できないことが多い。エラーメッセージの行番号 (Liquid は変換前の行) から原因の記号を探す。

## 検証 (verify) ファイルを書く

* 置き場所: アルゴリズム単体の検証は `verify/original/<Name>.test.cpp`、ジャッジの問題を使うものは `verify/<judge>/<category>/`。
* `verify/original` は `#define PROBLEM "https://judge.u-aizu.ac.jp/onlinejudge/description.jsp?id=ITP1_1_A"` を先頭に置き、`verify()` に `assert` を並べ、`main` で `verify(); cout << "Hello World" << endl;` とする (既存の `Double_Add_Convolution.test.cpp` などに倣う)。
* CI は `g++-13 -std=c++23 -O3 -Wall -g` で全件実行する。**ヘッダの API を変えたら、旧 API を使う検証ファイルが壊れていないか必ず確認する** (今回も、旧版の群用 API が残っていた)。
* 位数や既知の値との一致、作用表の整合性、小さい例での全探索との突き合わせなど、**実装と独立な根拠**でテストする。無限になる入力など、終了しないものはテストにしない。

## コミット・ブランチ

* `main` に直接コミットしない。ブランチ名は `feature/<name>` (ドキュメントのみなら `doc/<name>` もある)。
* コミットメッセージは `feature:` / `docs:` などの接頭辞 + 日本語の要約。本文に変更ファイルを列挙してよい。
* 関係のないファイル (他のトピックの未追跡ファイル) はコミットに含めない。プッシュや PR 作成は、頼まれたときだけ行う。
